# Engineering Standards (Harusari)

## 0. 기본 원칙
- 기본 개발 방식은 TDD로 한다.
- 핫픽스는 예외적으로 선조치 가능하되, 24시간 내 회귀 테스트를 반드시 보강한다.
- 기능 추가보다 안정성/가독성/회귀방지를 우선한다.

## 1. TDD 정책
- Red -> Green -> Refactor 순서 고정.
- 최소 단위 테스트 먼저 작성 후 구현.
- 버그 수정 시 "재현 테스트"를 먼저 추가한다.
- PR 머지 조건:
  - 신규 기능: 테스트 포함
  - 버그 수정: 회귀 테스트 포함
  - 기존 테스트 전체 통과

## 2. 아키텍처 규칙
- 경계 분리:
  - UI 계층: `app/*`, `components/*`
  - 도메인/비즈니스 로직: `lib/*`
  - 외부 연동(Supabase/API): `lib/*/adapters`
- 인증 로직은 단일 서비스 계층으로 수렴한다.
- 공통 정책(redirect/sanitize/session-check)은 util/service로 중복 제거.

## 3. 코드 컨벤션
- 함수는 단일 책임 원칙(SRP) 준수.
- 매직 스트링/매직 넘버 금지 (상수화).
- 에러 코드는 표준 포맷 사용: `L-{DOMAIN}-{DETAIL}`.
- 비동기 에러는 반드시 핸들링하고, 사용자 메시지와 내부 로그를 분리.
- lint warning 누적 금지(기존 경고는 점진 해소).

## 4. 디자인 패턴 가이드
- 서비스 계층 패턴: 인증/결제/푸시 등 핵심 흐름.
- 어댑터 패턴: 외부 SDK(Supabase 등) 의존성 캡슐화.
- 가드 패턴: 라우트 접근 제어/권한 체크.
- 전략 패턴: 로그인 provider(google/kakao) 분기 처리.

## 5. 테스트 피라미드
- Unit: 도메인 로직 중심 (빠르고 많이)
- Integration: 인증 흐름/DB 연동 핵심 경로
- E2E: 로그인, 세션 유지, 보호 라우트 접근

필수 회귀 시나리오(로그인)
1. 정상 로그인 성공
2. OAuth callback 실패 시 로그인 복귀
3. 만료 토큰 재진입 처리
4. 새로고침 후 세션 유지
5. 비정상 next 파라미터 차단

## 6. PR 체크리스트
- [ ] 재현 테스트 추가됨
- [ ] 구현 코드 최소 변경 원칙 준수
- [ ] 리팩토링으로 중복 제거
- [ ] 문서/관측 포인트 업데이트
- [ ] 롤백 방법 명시

## 7. 예외 정책 (핫픽스)
- 서비스 장애(P0/P1) 시 선조치 허용
- 단, 24시간 내 아래 완료 필수:
  - 회귀 테스트 추가
  - 원인/재발방지 문서화
  - 알람/대시보드 기준 반영
