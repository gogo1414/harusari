# 기획안: 고정 지출에서 '저축' 분리

작성일: 2026-07-03 | 상태: 검토 대기

## 1. 문제 정의

현재 적금·청약·투자 이체 같은 저축성 항목이 일반 고정 지출(월세, 통신비)과 같은 `fixed_transactions(type='expense')`로 저장된다. 그 결과:

- 고정 지출 목록에서 "진짜 나가는 돈"과 "내 자산으로 이동하는 돈"이 구분 안 됨
- 통계의 지출 총액에 저축이 섞여 실제 소비 수준이 과대 표시됨
- 저축률(수입 대비 저축) 같은 핵심 지표를 만들 수 없음

## 2. 설계 대안 비교

| | A. 제3의 type 'saving' | B. 거래별 is_savings 플래그 | **C. 카테고리 속성 (권장)** |
|---|---|---|---|
| 방식 | `type IN ('income','expense','saving')` | transactions/fixed_transactions에 boolean 컬럼 | `categories.is_savings boolean` — 저축 카테고리에 속하면 저축 |
| 스키마 변경 | CHECK 3곳 + 기존 행 마이그레이션 | 컬럼 2개 추가 | **컬럼 1개 추가** |
| 코드 영향 | `type === 'expense'` 분기 전수 수정 (폼, 통계, 캘린더, cron, 요약 카드 — 수십 곳) | 거래 생성 경로 전부(수동/백필/cron) 플래그 전파 필요 | **생성 경로 무변경, 조회 시 카테고리 join으로 판별** |
| cron 영향 | 있음 | 있음 (전파 로직) | **없음** |
| 일회성 저축 기록 | 가능 | 가능 | 가능 (저축 카테고리로 기록) |
| 위험 | @ts-expect-error 25건 상태에서 대수술 | 전파 누락 시 데이터 불일치 | 카테고리 미지정 거래는 판별 불가 (허용 가능) |

**권장: C안.** 이 앱은 이미 예산·통계가 카테고리 중심으로 동작하고, 거래 생성 경로(수동 입력·백필·cron)가 3벌 중복인 상태라 생성 경로를 건드리지 않는 설계가 가장 안전하다. 개선 보고서의 백필 로직 통합이 끝난 뒤라면 B안도 고려 가능.

## 3. C안 상세 설계

### 3-1. 스키마

```sql
-- categories에 저축 속성 추가
ALTER TABLE categories ADD COLUMN is_savings BOOLEAN NOT NULL DEFAULT false;

-- 기본 제공 저축 카테고리 (신규 유저용 기본 세트에 추가)
-- 예: 적금 🏦, 투자 📈, 비상금 🛟 (type='expense', is_savings=true)
```

타입 재생성: `npx supabase gen types typescript` (기존 타입 불일치 25건도 함께 해소).

### 3-2. 판별 규칙

- `저축 거래` = `type === 'expense' && category.is_savings === true`
- 카테고리 없는 거래(SET NULL 포함) = 일반 지출로 취급
- income 카테고리에는 is_savings 노출 안 함 (지출 탭 전용 속성)

판별 유틸을 단일 소스로 제공:
```ts
// lib/savings.ts
export const isSavings = (t: Transaction, categoryMap: Map<string, Category>) =>
  t.type === 'expense' && !!t.category_id && !!categoryMap.get(t.category_id)?.is_savings;
```

### 3-3. 화면별 변경

**카테고리 관리** (`app/categories/page.tsx`)
- 지출 탭의 카테고리 추가/수정 다이얼로그에 "저축 카테고리" 스위치 추가
- 목록에서 저축 카테고리에 뱃지(🏦 저축) 표시

**고정 내역 목록** (`app/recurring/page.tsx`) — 핵심 화면
- 현재: 수입/지출 2개 섹션 → 변경: **수입 / 고정 지출 / 저축** 3개 섹션 (또는 지출 섹션 내 저축 그룹 분리)
- RecurringSummary에 "월 저축액" 합계 추가: `월 수입 − 고정 지출 − 저축 = 가용액` 구조로 표시

**고정/거래 입력 폼**
- 변경 없음. 저축 카테고리를 선택하면 자동으로 저축으로 분류됨
- 선택 카테고리가 저축이면 폼에 가벼운 표시(예: 금액 아래 "저축으로 기록돼요") — 사용자 인지용

**홈 요약 카드** (`components/dashboard/SummaryCard`)
- 1단계: 유지 (지출에 저축 포함 — 현금 흐름 관점)
- 2단계(선택): 지출 카드에 "지출 45만 · 저축 30만" 병기

**통계** (`app/stats/page.tsx`)
- 지출 카테고리 차트에서 저축 카테고리 분리 → 별도 "저축" 카드
- 신규 지표: **저축률 = 저축 합계 / 수입 합계** (수입 0이면 미표시 — 0 나눗셈 주의, 개선 보고서 예산 0원 이슈와 동일 패턴)
- "소비 지출" = expense 합계 − 저축 합계로 재정의하고 라벨을 명확히
- 월별 추이 차트에 저축 라인 추가 (선택)

**예산/생존 예산** (`useDailySurvival`, budget)
- 생존 예산 계산은 이미 `!source_fixed_id`로 고정지출을 제외하므로 고정 저축은 자동 제외됨. 단, **일회성 저축 거래**는 현재 수동 지출로 잡히므로 `isSavings()` 필터 추가
- 저축 카테고리에는 예산 목표 대신 "저축 목표"로 표기 구분 (선택)

### 3-4. 기존 데이터 마이그레이션 (사용자 액션)

스키마만으론 기존 저축이 분류되지 않으므로:

1. 배포 후 첫 진입 시(또는 고정 내역 화면에서) 1회성 안내: "저축 카테고리를 지정하면 고정 지출과 분리해서 보여드려요"
2. 카테고리 관리로 유도 → 기존 카테고리(예: '적금')에 저축 스위치만 켜면 **과거 거래까지 소급 분류됨** (판별이 조회 시점 join이므로 데이터 수정 불필요 — C안의 큰 장점)
3. 이름에 '저축/적금/투자/청약'이 포함된 기존 카테고리는 안내 다이얼로그에서 자동 후보로 제시

### 3-5. 엣지 케이스

| 케이스 | 처리 |
|---|---|
| 저축 카테고리 삭제 | 거래는 SET NULL → 일반 지출로 회귀 (삭제 다이얼로그에 명시. 개선 보고서 3-8의 삭제 UX 수정과 함께 진행 권장) |
| 저축 카테고리를 일반으로 변경 | 과거 통계도 즉시 재분류됨 — 스위치 변경 시 "과거 내역 포함 재분류" 안내 |
| 저축 + 할부 조합 | 허용하되 의미가 모호하므로 폼에서 저축 카테고리 선택 시 할부 옵션 숨김 권장 |
| invalidation | 카테고리 수정 시 `['categories']`만으로 부족 — 통계·목록이 카테고리 기반 재분류되므로 `['transactions']`, `['fixed_transactions']`도 무효화 |

### 3-6. 단계별 실행 계획

1. **P1 (스키마+분류)**: 컬럼 추가, 타입 재생성, 카테고리 관리 스위치+뱃지, `lib/savings.ts` + 단위 테스트
2. **P2 (핵심 가치)**: 고정 내역 3섹션 분리, RecurringSummary 저축 합계, 기존 카테고리 마이그레이션 안내
3. **P3 (통계)**: 저축 카드·저축률, 소비 지출 재정의, 생존 예산 필터
4. **P4 (선택)**: 홈 요약 병기, 추이 차트 저축 라인, 저축 목표

### 3-7. 테스트 계획

- 단위: `isSavings()` (카테고리 없음/일반/저축/income 케이스), 저축률 0 나눗셈
- 컴포넌트: RecurringList 3섹션 분기, 카테고리 스위치 토글
- E2E: 저축 카테고리 생성 → 고정 등록 → 목록 분리 표시 → 통계 저축 카드 반영
